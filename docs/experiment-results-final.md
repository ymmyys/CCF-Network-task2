## 算法修复（本轮关键改进）

本轮在实验中发现两个核心问题并完成修复：

### 修复1：schedulingState 严格化（backend.go）
**问题**：`healthy=false` 时，旧代码仍返回 `(weight, false)`，其中 `ok=false` 仅当 `healthy && weight>0` 同时为 true。当 backend 刚被 docker stop 但 health check 尚未执行时，`healthy=true` 且 `effectiveWeight` 仍>0，后端仍可被调度——这导致 exp4 故障后 npu5 仍有 11.7% 流量。

**修复**：
```go
// 新：unhealthy 或 passive 熔断中 → 立即不可调度
if !healthy || now.Before(passiveUntil) {
    return 0, false
}
```

### 修复2：P2C 采样逻辑改为 withReplacement（scheduler.go）
**问题**：旧 P2C 用 `weightedSample(total-first.weight, exclude=first)` 做第二次采样。2 后端时 exclude 掉唯一另一个后端后采不到，fallback 到 `bestCurrentCandidate`，两个候选实为同一后端——P2C 完全退化。

**修复**：
```go
// 新：两次独立采样（with replacement）
first  := weightedCandidate(candidates, total, nil)
second := weightedCandidate(candidates, total, nil)
if first.slot == second.slot { return first }   // 同一后端→直接用
return betterP2CCandidate(first, second)        // 不同→loadScore比较
```

## 结论边界

- exp1 的 direct-to-vLLM 是单后端参考，router 组是 2 后端对照，不做严格横向优劣比较。
- exp2 证明 P2C 具备慢节点避让能力，但当前策略偏激进，会带来 QPS 和 p50 代价，不能表述为全面优于 SWRR。
- exp6 未重跑且统计窗口未拆分，不作为核心证据。
- exp7 的 `smoothStep=0.25` 是本轮 5 后端实验里的较优默认折中，不表述为所有场景下的绝对最优。

## 实验1：正常均衡场景（三组对照）

### 目的
证明动态调度在正常场景下无明显额外开销。

### 结果

| 组别 | 请求 | QPS | p50 | p95 | p99 |
|------|------|-----|-----|-----|-----|
| direct-to-vLLM (1后端) | 8,081 | 134.68 | 238.80ms | 285.49ms | 308.49ms |
| router + swrr (2后端) | 14,057 | 234.28 | 134.87ms | 151.23ms | 195.68ms |
| router + p2c_smooth_wrr | 14,038 | 233.97 | 134.80ms | 153.24ms | 199.06ms |

### 结论
p2c_smooth_wrr 相比 swrr：QPS 基本持平，p50 差 0.07ms，p95 差约 2ms，p99 差约 3.4ms（约 1.7%），说明正常均衡场景下无明显额外开销。direct-to-vLLM 是单后端原始性能参考，不与 2 后端 router 组直接比较。

## 实验2：异构负载场景（重跑 ✅ 真实慢后端）

### 目的
验证 P2C 动态调度能主动避开慢节点，并记录这种激进避让策略带来的吞吐和中位延迟代价。

### 设置
- fast backend：vLLM npu3（端口 9021，真实推理）
- slow backend：fake_backend（端口 9023，sleep 300ms，利用率 90%，queue_depth=16）
- 并发 32，持续 60s

### 结果

| 调度器 | 请求 | fast-npu3 | slow-fake | p50 | p95 | p99 |
|--------|------|-----------|-----------|-----|-----|-----|
| swrr | 8,826 | 51.1% | 48.9% | 150.4ms | 303.7ms | 304.8ms |
| p2c_smooth_wrr | 7,725 | 100% | 0% | 251.4ms | 285.2ms | 300.4ms |

### 结论
- ✅ P2C 通过 loadScore 比较（inflight/latencyEWMA/queueDepth），将慢后端流量从 48.9% 完全降到 0%
- ⚠️ QPS 下降（147→129），p50 从 150.4ms 升到 251.4ms，原因是本实验中策略将 slow-fake 流量降为 0% 后只剩 1 个 fast 后端处理全部请求
- ⚠️ 因此 exp2 证明的是慢节点避让能力，不证明 P2C 在所有指标上全面优于 SWRR。后续优化方向是增加 `p2c_balanced` 策略，对慢节点保留少量受控流量以改善吞吐和 p50 折中

## 实验7：smoothStep 参数敏感性（重做 ✅ 5后端）

### 目的
验证 smoothStep 参数选择的合理性，并找到适合本实验拓扑的默认折中值。

### 设置
- 5 后端（npu3-7），降容 npu3 10→1

- smoothStep 取值：0.10 / 0.25 / 0.50 / 1.00

| 0.50 | 246.2 | 19.9% | 2.1% | 2.44% | -0.34pp | 1.7pp |

### 每秒 npu3 占比（ss=0.25）

| 秒 | npu3 占比 | 观察 |

### 对比分析

| smoothStep | 收敛速度 | 平滑性 | 评价 |
|------------|----------|--------|------|

### 结论
✅ **smoothStep = 0.25 是较优默认折中**：降容后稳定占比 2.4% 与理论值 2.44% 误差仅 0.04pp，在收敛速度和平滑性之间取得较好平衡。该结论限定在本轮 5 后端实验，不表述为所有场景下的绝对最优。

4. **故障场景**：2-3 秒完成故障摘除，72,887 请求仅 7 个失败（0.01%）
5. **恢复场景**：slow-start 避免流量尖峰，逐步恢复到均衡
6. **隔离场景**：资源池完全隔离，default 池不受高压租户影响
7. **参数选择**：smoothStep=0.25 在本轮 5 后端实验中是较优默认折中
